# media_integration

Thin adapter between the player and the OS "now playing" surfaces: macOS Control Center / Lock Screen and media keys (`MPNowPlayingInfoCenter`, `MPRemoteCommandCenter`), Windows System Media Transport Controls (`souvlaki`), Linux MPRIS (our own service on pure-Rust `zbus` 5, no libdbus). It makes no playback policy decisions; the only state it keeps is what MPRIS has to answer from. Outbound, the app pushes `NowPlayingInfo`, `MediaPlaybackState`, elapsed time and (MPRIS only) its volume; inbound, the OS sends `MediaCommand`s down a `flume::Sender` the caller supplied.

Not here: mapping engine events to these calls, the receiving end of the command channel, spawning the Linux driver and the integration's owner (`crates/pawse/src/doc.md`: `media_bridge.rs`); writing the cover file the OS reads (`LibraryService::get_cover_art_path_for_media`, same doc).

## Files

- `lib.rs` — `SystemMediaIntegration`, the data types, `create_integration(sender, hwnd)` → `Integration { controls, driver }` (cfg-dispatched; `None` where there is no backend or init fails; `driver` is `Some` only on Linux). Re-forbids `unsafe` off macOS.
- `souvlaki_backend.rs` — `SouvlakiIntegration`, Windows only: `map_event` (OS event → `MediaCommand`; Stop, Raise, Quit, volume and relative seek are ignored) and `playback`; dropping it calls `detach`. Unit-tested.
- `mpris/state.rs` — pure MPRIS state: status, track (with its trackid number), the live and the announced position anchors, the volume; every update returns the `Changes` it caused; `VolumePacer` (when a volume change may be signalled); seek-command math and the `file://` URL encoding. Built for tests on every OS, so its unit tests run on macOS too.
- `mpris/interfaces.rs` — the `org.mpris.MediaPlayer2` and `.Player` D-Bus interfaces (`zbus::interface`), the shared state they read and the `Changes` → `PropertiesChanged` payload.
- `mpris/service.rs` — `MprisIntegration` (the trait impl on the UI thread) and the driver future: connect, take the bus name, emit signals (volume through the pacer and an `async-io` timer), tick zbus's executor.
- `macos/mod.rs` — `MacOsIntegration`: artwork cache and the trait impl; no `unsafe` of its own.
- `macos/now_playing.rs` — `MPNowPlayingInfoCenter` writes (full metadata vs. position only) and artwork loading.
- `macos/remote_command.rs` — `MPRemoteCommandCenter` handler registration.

## Rules

- Main thread only. AppKit / MediaPlayer singletons have main-thread affinity and `souvlaki::MediaControls` is `!Send`. `MacOsIntegration::new` needs a `MainThreadMarker`; the integration is an `Rc<dyn SystemMediaIntegration>` and never crosses threads. Only the `flume::Sender` leaves it, captured by the OS callbacks. On Linux the D-Bus side runs in the driver; the two share `Arc<Mutex<mpris::State>>`, locked only for a copy or a diff, never across an `.await`.
- Commands go through the channel, never a direct call. OS callbacks (ObjC blocks, souvlaki's `attach` handler, D-Bus method calls) can fire at any time; they only do a non-blocking `send`, which keeps them off GPUI's runtime and its internal locks.
- Two update paths, deliberately asymmetric. `update_now_playing` rebuilds the full metadata once per track; `update_position` is the hot path (every engine position tick) and on macOS only patches elapsed time and rate onto the existing dictionary, on Linux only re-anchors the position in memory.
- Playback rate freezes the macOS scrubber. Control Center advances from the reported rate, not the playback-state flag, so `update_now_playing` and `update_position` derive the rate from `MediaPlaybackState` (1.0 playing, 0.0 otherwise); a paused track must report 0.0 or the widget keeps scrubbing. That is why `update_now_playing` takes the state. The souvlaki path has no rate; it passes the state with the progress.
- Progress is sanitized before it reaches the OS: durations and elapsed values go through only when finite and non-negative (duration also positive). `Duration::from_secs_f64` panics on `NaN` / `inf`, and `NowPlayingInfo`'s `f64` fields are not validated. MPRIS ignores an invalid elapsed value and keeps the last anchor.
- MPRIS signals only on real change. Every client may act on every `PropertiesChanged` (KDE Connect forwards each one to the phone, which keeps it awake), so the UI thread sends to the driver only when a `State` update returned non-empty `Changes`, and the driver merges whatever queued up into one `PropertiesChanged` with current values, then `Seeked`. A position tick at the expected place changes nothing; `update_now_playing` → `set_playback_state` → `update_position` for one track is one signal.
- MPRIS `Position` is computed on read and never signalled (spec: `EmitsChangedSignal=false`, clients extrapolate with `Rate`): the live anchor (last reported position) plus the time since it while Playing, frozen while Paused, 0 while Stopped, clamped to the length. `Seeked` fires when a reported position is more than `SEEK_TOLERANCE_SECS` (1 s) away from the announced anchor (the last `Seeked`, status change or new track, extrapolated, unclamped) and carries the new announced position. Measuring from the announcement, not the previous tick, keeps what clients extrapolate within the tolerance after slow drift or a burst of late ticks. 1 s catches seeks from any source and a stalled stream and stays above tick jitter (~200 ms of written audio, ring buffer 128 ms). A new track resets the position without `Seeked`.
- MPRIS `Volume` belongs to the app. A client's write only sends `MediaCommand::SetVolume` (clamped to `0..=1`, non-finite dropped); the property changes when the app reports its volume through `SystemMediaIntegration::set_volume` (a no-op on the other backends), so every client and the app's own slider show one value. A write the app refuses changes nothing; the app answers it with `restate_volume`, which signals the unchanged value once so the client's slider goes back (the one exception to "signals only on real change"). Values are rounded to 0.01, the app slider's step: the `f32` → `f64` noise of a round trip is not a change.
- `Volume` signals are paced: the first change goes out at once, later ones not sooner than `VOLUME_SIGNAL_INTERVAL` (200 ms) after the previous, as one signal with the value current at that moment; a value back at the last signalled one sends nothing, and the pacer starts from the volume the state held when the driver connected, which clients read with the other properties. Restated values are paced the same way. A slider drag is up to 100 steps in the app and ~90 writes from a KDE Connect phone, each of which would otherwise go to the phone.
- `Volume` is declared `EmitsChangedSignal=false` although we do signal it: with `true`, zbus's generated setter emits `PropertiesChanged` itself after every write, with the value from before the app applied it. Clients listen for the signal regardless of the annotation.
- MPRIS trackids are `/io/github/popovpsk/pawse/track/<n>`, a new `n` per distinct metadata (spec: unique, not under `/org/mpris` except the `NoTrack` sentinel); the same metadata again keeps the id. `SetPosition` with another trackid or out of `0..=length` is ignored; `Seek` and `SetPosition` need a known length, which is also `CanSeek`.
- zbus stays on `async-io` (`system_tray/src/doc.md`: its `tokio` feature would switch every zbus user in the build) and owns no thread: the connection is built with `internal_executor(false)` and the driver ticks `Connection::executor()` while it pumps signals, all on whatever executor the caller polls it on; async-io's reactor thread is shared with the other zbus users.
- The bus name is `org.mpris.MediaPlayer2.pawse` (the Flatpak manifest's `--own-name`), requested with `DoNotQueue` and without `AllowReplacement` / `ReplaceExisting`, which zbus's builder sets by default: nobody takes it from us, we take it from nobody. No session bus or the name taken → the driver logs a warning and ends, the integration stays inert; dropping `MprisIntegration` closes the change channel, which ends the driver and releases the name.
- `DesktopEntry` is `$FLATPAK_ID` inside the Flatpak (`io.github.popovpsk.pawse`), otherwise `pawse`, the `.desktop` name cargo-packager gives the Linux packages and the window `app_id`.
- `unsafe` stays on macOS. The crate allows it (`objc2`), but `lib.rs` has `#![cfg_attr(not(target_os = "macos"), forbid(unsafe_code))]`, so the facade, the souvlaki backend and MPRIS stay provably safe; only `macos/now_playing.rs` and `macos/remote_command.rs` use it.
- Degrade to nothing: `create_integration` returns `None` for an unsupported platform, a souvlaki create/attach failure, or a call off the main thread on macOS. Windows needs `hwnd` for SMTC; every other platform ignores it.
- The artwork file must live where the host can read it. `NowPlayingInfo::artwork_path` is a filesystem path; MPRIS gets it as a percent-encoded `mpris:artUrl = file://<path>`, which the desktop shell resolves outside our process. So the app writes it under `dirs::cache_dir()/pawse/artwork`, never `std::env::temp_dir()`: inside a Flatpak `/tmp` is the sandbox's private tmpfs, a `file:///tmp/...` URL points at nothing on the host, and a host file with the same name would show someone else's cover. Windows SMTC and the macOS widget consume the same path.
- The integration must outlive playback, which goes on with no window (macOS, and the tray on Windows and Linux): on macOS and Linux it is app-lived; on Windows it is rebuilt for whichever window exists, the main one or the tray's hidden one, because SMTC belongs to an `hwnd`. `SouvlakiIntegration`'s `Drop` detaches: souvlaki's Windows controls have no `Drop`, so a dropped one would stay enabled with its button handler, and the next integration on the same window would add a second handler (one media key, two skips).

## Decisions

Owner's calls; ask before changing.

- Linux MPRIS is our own service, not souvlaki: souvlaki emits `PlaybackStatus` on every position update and has no extrapolated `Position`. Windows stays on souvlaki.
- Relative `Seek` is supported (KDE Connect's seek bar sends `Seek(target − Position)`); past the end it acts as `Next`, as the spec says.
- MPRIS `Volume` is the app volume, read and write, with the app as the only source of truth (KDE Connect's volume slider). Not on Windows or macOS.
- `Stop` pauses.
- No `Raise`: `CanRaise` is false (reusing the tray's Show was floated for later).
- No D-Bus contract test on macOS: `mpris/state.rs` is unit-tested, the D-Bus side is checked by hand on Linux.
